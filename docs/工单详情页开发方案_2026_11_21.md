## 0. 结论摘要

1. **页面只有三块**：工单头（身份与当前位置）→ 调用链（它是怎么走到这一步的）→ 交付（结果、验收、用量）。来源、审批、中断都**并进调用链**，不再各占一张文字卡片。
2. **调用链是「影响图」，不是工作流 DAG**：点 = 一个 Agent（会话），线 = 一次**有地址的主动投递**。工具返回、后台完成通知是「回执」，默认不画。这条区分不需要我们自己定义——DSH 已经把它写进了会话日志（`agent-message` vs `subagent-settled`）。
3. **不需要新埋点**：同一工单的多个 Agent = 同一棵会话树。`subagent/catalog`（父会话里的子代理目录）给出树，`agent-message`（带 `senderSessionId`）给出边，L2 账本给出生命周期与审批。这个页面本质上是**一份投影**。
4. **图形用 DOM 行 + SVG 装饰，不用 canvas**：540px 窄栏里文字、i18n、命中区、读屏、测试都靠行；弧线只是装饰层。这样「一条直线」就是真的直线，可测、可访问、可随时加行。
5. **因果要诚实**：日志只能证明「时间上后发生 + 结构上相关」。UI 把「事实」（收到了什么、之后做了什么）与「推断」（可能由它引起）分开标注，不假装知道动机。

## 1. 这个页面要回答什么

| 问题 | 用户在场时的真实意图 | 页面答案 |
|---|---|---|
| 它在哪？ | 卡住了吗？还在跑吗？跑到第几步？ | 阶段徽标、当前轮次/等待对象、调用链末尾的 live 行 |
| 它是怎么来的？ | 谁让我做这件事？依据是什么？ | 链首「来源 → 路由派发」两行 |
| 谁在干、谁跟谁说话？ | 为什么有 4 个 Agent？谁听谁的？ | 团队 chips + 泳道 + 扇出弧线 |
| 为什么卡住/变慢？ | 是在等人、等子代理、还是被打断？ | 审批行、中断行、live 行的等待对象 |
| 它做成了什么？ | 能验收吗？花了多少？ | 交付卡：汇报、对照验收标准、轮次/投递/时长/token |
| 这条信息影响了什么？ | 审计、追溯、复盘 | 点线就地展开：全文、收到后做了什么、影响范围、会话定位 |

**成功标准（假设）**：打开详情页 3 秒内能说出「现在在等谁」；不用读原始日志就能解释一次返工；能从任一投递跳到两个 Agent 的会话。

## 2. 关键概念：影响图 vs 工作流

### 2.1 三层图，别混在一起

- **意图层（工作流 DAG）**：Leader 拆了哪几个任务、谁负责、依赖是什么。若开了 Team 模式，DSH 已有共享任务板（`team/task`，投影 `agentTeam`）。
- **影响层（调用链）**：谁对谁说了什么、谁因此改变了下一步。**本页的主角。**
- **结果层（交付物）**：汇报、文件、测试、审批记录。

三层可以互相引用，但不要画在同一张图里。任务板回答「计划」，调用链回答「实际」。

### 2.2 边的定义：有地址的主动投递

一条边成立需要三个条件：**有发送者、有接收者、由 Agent 主动发起**。

| 事实 | 算边？ | 理由 |
|---|---|---|
| `send_message` 发给树内某个 Agent | ✅ | 有明确接收方，接收方会因此改变下一步 |
| Leader 派生子代理（带任务 prompt） | ✅ | 这是一次任务投递，接收方是新会话 |
| 人类审批/回答（`user-approval`） | ✅ | 明确改变了执行分支 |
| 子代理完成通知（`subagent-settled`） | ❌（回执） | 运行时对结果的账，不是发送方的表达 |
| 工具返回（`tool/result`） | ❌（回执） | 环境返回，不是 Agent 的主动表达 |
| 文件变化、定时器、感知事件 | ❌（外部输入） | 是工单的「来源」，不是工单内部的边 |
| 普通 fork / 用户手动开新会话 | ❌ | 不在这棵协作树里（`origin` 不是 `subagent`） |

> 这条区分不是我们发明的：`dsh-subagent/src/continuation-messages.ts` 里 `AgentMessageSource{kind:'agent-message'}` 的注释明确写着「agent message 是发送方选择的内容，completion notice 是运行时对子级结局的账；把两者合并会把子级没说过的话记在它头上」。照抄这个判断即可。

### 2.3 同一工单里为什么会有多个 Agent

- 工单只绑定**一个** worker 会话（L2 `task/dispatched.workerSessionId`），它是记账单位。
- worker 面对复杂任务可以**自己当 leader**：用 subagent 工具派生可继续子会话，自己做编排。
- 每个子代理是**独立会话**（`parentSession` 指向父会话、`origin:'subagent'`），有自己的日志、轮次、token。
- 父会话日志里的 `subagent/catalog` 记录每个子级的 `childId`、`name`、`createdAt`；子级的消息里记录 `senderSessionId`。**树与边都在这两份日志里，不需要新协议。**

因此「4 个 Agent」不是 4 个 worker，而是 **1 个负责人 + 3 个子代理会话**。页面必须把角色说清楚：负责人 = 工单绑定的 worker；子代理 = 它派生的会话。

### 2.4 因果的边界

日志能证明的只有：

- **投递事实**：A 在 seq x 发了什么，B 在 seq y 收到了；
- **时序与结构**：B 收到后先做了什么（派发、审批、再上报、结束）；
- **树的形状**：谁派生谁、谁是祖先。

日志**不能**证明动机。所以「影响范围」的算法是启发式：从接收方出发，取它在**下一次收到同发送方的消息之前**（或本回合结束前）产生的主动投递与结构性动作，递归下去。UI 上明确分两栏：

- **事实**：收到后它做了什么（工具调用、派发、审批、上报、结束）。
- **推断**：后续 N 条投递可能由它引起（可点，标注「推断」）。

## 3. 图形设计

三种候选已在 `collab/img/ticket-detail-models.png` 中并排对比。

### 3.1 方案对比

| | A 时序泳道（推荐） | B 拓扑点线 | C 因果缩进树 |
|---|---|---|---|
| 读法 | 时间向下，泳道 = Agent | 点 = Agent，线 = 影响关系 | 每条投递的「后代」缩进 |
| 过程/当前位置 | ✅ 天然 | ❌ 丢失 | ❌ 打乱 |
| 并行/扇出 | ✅ 一眼可辨 | ⚠️ 聚合成「派发 ×3」 | ✅ 但按深度优先 |
| 因果归因 | ⚠️ 需高亮下游 | ⚠️ 只有关系 | ✅ 最直接 |
| 窄栏适配 | ✅ 列固定、行短 | ⚠️ 节点卡片占宽 | ✅ 纯缩进 |
| 长链 | ✅ 纵向滚动 | ⚠️ 节点变多会挤 | ⚠️ 深缩进会挤 |
| 结论 | **主视图** | 收进「结构」开关 | 只放进单条投递的展开 |

### 3.2 主视图几何（A）

- **坐标**：x 是 Agent 泳道（固定顺序：人 → 负责人 → 子代理按创建顺序；每道 16px），y 是**等距行**（不是真实时间轴）。
- **行高**：里程碑 24px、单条投递 32–34px、并行扇出 46–50px、live 24px。
- **主行**（`hop`）：左侧泳道里的「起点圆点 → 贝塞尔弧线 → 箭头/终点圆点」，右侧 `from → to + 类型 + 摘要 + 时间`。
- **扇出行**（`fan`）：同一发送者、10 秒内、同一批的 N 条投递合成一行：一个起点、N 条弧线、N 个终点；右侧给「并行派发 ×3」与三项任务的短名。这就是你最初说的「大点连 3 个小点」。
- **里程碑**（`milestone`）：没有弧线，只有泳道上的空心点：简报投递、中断/恢复、汇报、关闭。
- **回执**（`passive`）：不画弧线，默认折叠为一条灰色里程碑（「reviewer 结束 · 回执」）；开关叫「显示回执」时才画虚线弧。
- **长空档**：不按真实时间留白，插一行「⏱ 6 分钟后」的分隔，保证「一条直线」在任何时长下都是直线。真实甘特留作后续。
- **live 行**：链尾的脉冲点 + 等待对象（「等待中 · frontend 正在第 2 轮」）。它就是「当前位置」。

### 3.3 为什么不用 canvas

- 行是 HTML `button`：可聚焦、可读屏、可复制、可 i18n、可被测（Vitest/jsdom 能断言行数、类型、时间）。
- 540px 的栏宽意味着**文字是主体**，图形只是 96px 的左侧轨道；canvas 反而要自己解决命中和文字。
- 弧线只是装饰：`aria-hidden` 的 SVG，命中区是整行。
- 规模上限是几十行（一个工单的投递量），DOM 完全够；真到几百行再虚拟化。

### 3.4 行解剖（字段）

```
[泳道 96px]                             [内容 1fr]
  ●(发送方)  ╲
              ╲  (一次投递)             reviewer → lead   [上报]        09:18
               ●(接收方)                契约字段名不一致，建议改 schema…
```

- 发送/接收用 Agent 色 + monospace 名字；
- 类型**由会话树位置推导**，不调用模型：向下 = 派发，向上 = 上报，横向 = 同步；审批 = 审批/批准；
- 摘要 1 行（全文在展开里），时间 9.5px 右对齐；
- 右侧可挂事实徽标：「影响 2」或「由此引起」。

### 3.5 交互

- **点行**：就地展开（不跳页、不弹层）——全文、收到后做了什么、影响范围（缩进树）、两个会话的「定位」按钮。
- **点芯片/圆点**：Agent 卡片（状态、轮次、token、当前步骤、打开会话、只看这个 Agent）。
- **悬停**：1 行摘要 tooltip；**键盘**：Tab 聚焦行，Enter 展开，Esc 收起。
- **筛选**：显示回执 / 只看主干（隐藏没有主动投递的 Agent）/ 只看某 Agent（其余降低透明度，不断连）。
- **长链**：链内滚动上限约 420px，底部渐隐 + 「展开全部」；同一对 Agent 连续的同类投递折叠为「×3」。
- **新投递**：运行中每 2s 轮询，新增行淡入；若用户已向上滚动，显示「↓ 2 条新投递」而不抢滚动。
- **空态**：
  - 排队中：链首显示「等待放行 · 名额已满」，没有 live 行；
  - 单 Agent：一条直线 + 里程碑 + 「0 次投递」；
  - 日志不可读：链区降级为「无法读取会话日志」+ 保留 L2 里程碑；
  - 失败：链尾红色终点 + 失败原因。

### 3.6 540px 的硬约束

- 泳道 96px（最多 8 道，每道 11px），内容 392px；
- 一行最多两层信息（top 10.5px / 摘要 11.5px），不换行；
- 头部元信息一条 10.5px、用 `·` 分隔，放不下时换行而不是截断；
- chips 一行放 5 个（编号+名字+状态点），第 6 个起换行；
- 选中态就地展开，不新增右侧面板（窄栏没有第二列）。

**为什么把来源放进调用链**：来源是「因果的上游」，放在链首才能一眼读完「为什么有这单 → 谁先说话 → 卡在哪」；单独一张来源卡会变成第二份文字排版。审批、中断同理，都是链上的行。

> v1 不渲染「结构」开关（v1.1 再加）；上图保留它的位置只是为了说明版式。

**头部**只保留身份与状态：短码、标题、阶段、负责人、Agent 数、投递数、时长、打开会话。工作目录、会话 id、账本事件收进折叠区。

## 6. 数据与接口（可行性）

### 6.1 数据来源

| 数据 | 来源 | 备注 |
|---|---|---|
| 工单身份/阶段/时间/汇报 | L2 账本 | 已有 `TicketView`、`project()` |
| 来源（信号 → 决定） | L2 `signal/received` + `decision/recorded` | 按 `ticketId` 反查 |
| 审批请求/决定 | L2 `approval/*` | 已有 |
| 负责人会话 | `task/dispatched.workerSessionId` | 已有 |
| 子代理树 | 负责人会话日志的 `subagent/catalog` | `childId/createdAt`；v3 起带 `name`，旧版本回退到会话 id |
| 投递边 | 各会话日志的 `user/message`，`source.kind==='agent-message'`（`senderSessionId`） | 主动投递 |
| 回执 | `source.kind==='subagent-settled'` | 不画弧线，折叠成一条灰色里程碑（「reviewer 结束 · 回执」） |
| 审批送达 | `source.kind==='user-approval'` | 人类 → Agent |
| 轮次/token | `turn/start`、`assistant/message.usage` | 聚合 |
| 团队任务板（可选） | `team/task`（仅 Team 模式） | 后期作为「计划」对照 |

> 关键：**不要新增一套消息埋点**。DSH 的 subagent 运行时已经把树、主动投递、回执分别记进日志；PA 只需要读。

### 6.2 推导算法（早期草案，精确版见第二部分 §6）

> 下面这一段是最初的草案，已被第二部分 §6 取代；保留它是为了解释推导的分层与裁剪思路。

```
detail(ticket):
  root = ticket.workerSessionId
  lanes = [root] + catalogChildren(root) 递归，按 catalog 顺序
  rows = []
  for each session in lanes:
    events = live(session) ?? readLog(session)      // 按 ticket 窗口裁剪
    rows += {
      catalog:   spawn 行（父 → 子）
      agentMsg:  hop 行（from=senderSessionId, to=session）
      settled:   passive 行（默认不渲染）
      approval:  审批行（L2 为准，L1 补 anchor）
      turns:     里程碑（只保留中断/恢复/汇报/关闭）
    }
  rows = 按时间排序，同秒按 (lane 顺序, seq)
  rows = 合并同一发送者 10s 内的连续投递为 fan 行
  rows += live 行（若工单未结束）
```

裁剪规则很重要：`append` 模式会让多张工单共用一个 worker 会话，**必须按本单 `dispatchedAt → endedAt` 的时间窗过滤**，否则会把上一单的历史算进来。子代理在窗口内跨单发消息属于可接受的噪声。

### 6.3 接口（早期草案，精确契约见第二部分 §5.4）

> 下面这个形状是最初草案；实际实现以第二部分 §5.4 的类型为准（含 `mode`、`lanes`、`rows`、`completeness`）。

新增 `GET /personal-agent/api/tickets/:id`，返回：

```ts
interface TicketDetailResponse {
  ticket: TicketView
  origin?: { signal?: {...}; decision?: {...}; requestedBySessionId?: string }
  lanes: AgentLaneView[]   // 含 human；router 单独一条派单轨，不算 Agent 泳道
  rows: ChainRow[]         // hop / fan / milestone / passive / live / dispatch / supplement / continue
  delivery: { report?: string; expectedOutput?: string; outcome?: ...; usage: {...} }
  metrics: { agents: number; hops: number; parallel: number; pingPong: number; turns: number; tokens: number }
  completeness: { logs: 'full' | 'partial' | 'unavailable'; reason?: string }
  generatedAt: number
}
```

- 缓存：`ticketId → {maxSeq, at, detail}`；运行中 2–3s、已结束 60s；日志 `maxSeq` 不变则直接复用。
- 读日志：优先 `ctx.agents.get(id)?.session.snapshotEvents()`（活着），否则 `sessionPersistence`（`log-reader.ts` 已有）。
- 体积：每条投递摘要 200 字 + 展开全文 ≤ 4000 字；单会话最多回看 3000 条事件。
- 降级：日志不可读时 `completeness.logs='unavailable'`，只画 L2 里程碑，并给出「会话已归档/日志不可读」说明。

### 6.4 已知集成风险：消息级定位

`actions.openSession(sessionId)` 只能打开会话。DSH 的 chat 有 turn/step 级导航（`ChatNavigation` + `TurnJump`），但目前不是插件可调用的公开面；消息行也没有稳定的 `data-seq` 可抓。建议：

## 10. 最终模型：四个动作（2026-11-21 定稿）

### 10.1 动作表

| action | 中文 | worker | 投递 | 工单 | 图里的行 |
|---|---|---|---|---|---|
| `dispatch` | 派发 | 新 worker | `followup` | 新建 | 链首「派发」 |
| `append` | 追加 | 旧 worker（排队） | `followup` | 新建 | 链首「追加」+ 排队里程碑 |
| `supplement` | 补充 | 当前工单的 worker | `steer` | **不建** | 链中「补充」 |
| `reply` | 响应 | 不派单 | — | 不建 | 不在工单链里 |

两条硬规则：

- **投递方式由动作固定**，不做参数矩阵：没有 `dispatch × steer`，也没有 `supplement × followup`。
- **派发和追加的唯一区别是 worker 是否复用**。两者都是一次独立执行，各有自己的工单与详情页；追加单不并入上一张单。

### 10.2 为什么这套模型自洽

- **追加的「排队」正好是现有 `planDispatch` 的 busy 门**：同一会话同时最多一张未结束工单。两张单不会在时间上重叠，各自的链天然干净，observer 的汇报归属也不会打架。
- **补充的「插话」用 `agent.steer`**：下一个 step 边界生效，不打断长工具；不建单，所以不占槽位、不进队列、不抢汇报。
- **派发的「新 worker + followup」**就是现状。
- **忽略不在决定枚举里**：它在来源层被过滤（`signal/received.delivered=false`），根本没到达 router。保持这个不变量，不要给 `decision/recorded` 加 `ignore`。

### 10.3 追加单的详情页

- 链首是「追加」行（R → lead），时间取 `dispatchedAt`；之前可以有「入队 · 等待 worker 空闲」里程碑（取 `createdAt`）。
- 会话日志里包含上一张单的历史：**必须按 `dispatchedAt → endedAt/now` 裁剪**。子代理树按「窗口内参与」裁剪：窗口内有 catalog 条目或 agent-message 的子会话才进图——复用的旧子代理如果在本单里说过话，也要进；只按 `createdAt` 过滤会漏掉它们。
- 上一张单不在本图里；「会话与目录」折叠区给一句「本会话另有 N 张工单」。
- 头部 meta 加「复用会话」；不跨单画弧线。

### 10.4 补充的详情页

- 行：`R → lead [补充]`，摘要即正文，展开是全文 + 「收到后它做了什么」+ 影响范围。
- 固定 `steer`，所以没有「插话/排队」选项；行详情写「插话 · 下一步生效」。
- 工单处于 `queued` / `ended` 时不允许补充（没有可送达的 worker）；错误码提示改用 append/dispatch。
- 补充不改变工单生命周期；若因此起了一个回合，回合结束仍按原规则汇报/关闭。

### 10.5 事件与工具

- `DECISION_ACTIONS` 增加 `supplement`；`decision/recorded { action: 'supplement', signalId, ticketId }`。
- 新事件 `task/supplemented { ticketId, targetSessionId, text, requestedBySessionId, messageId? }`（无 `mode`，固定 steer）。
- 新工具 `pa_ticket_supplement({ ticketId, text, signalId? })`：校验工单未结束、worker 在线；claim 信号；**先送达、后记账**。
- `deliverToSession` 增加可选 `target: 'followup' | 'steer'`，默认 `followup`；派发/追加用 followup，补充用 steer。
- 投递消息的 source 增加可选 `ticketId` / `supplementId`；现有任务简报也补上 `ticketId`（现在只能从 messageId 里的 `pa-ticket-delivery:<id>` 反解）。
- 事件页：处理方式下拉增加「补充」；补充结局可点跳工单（与派发/追加一致）。

### 10.6 对 V1 的影响

- **V1 拆两刀**：
  1. 动作模型 + supplement 工具/投递/事件页（Host + 事件页小改）；
  2. 详情页（过程视图 + R 轨 + 派发/追加/补充行）。
- **结构模式**仍 V1.1。
- **不做**：跨单时间线、append 护栏（不需要，busy 门已经保证串行）、supplement 的 delivery 选项。

## 3. 定稿决策（不可变）

1. **四个动作**：`dispatch`（派发，新 worker）/ `append`（追加，旧 worker，排队）/ `supplement`（补充，当前工单，插话）/ `reply`（响应）。`ignore` 留在来源层，不进决定枚举。
2. **投递方式由动作固定**：dispatch/append = `followup`；supplement = `steer`；**没有** `delivery` 参数。
3. **dispatch 与 append 都创建工单**，唯一区别是 worker 是否复用。两张单是**独立执行**，各有自己的详情页；追加单**不并入**上一张单。
4. **只有 supplement 影响泳道图**；worker 复用不影响图（lane 名字相同即可）。
5. **Router 是派单轨（R 轨）**：最左侧细轨，只承载派发/追加/补充行；无轮次、无状态，可点开 router 会话。
6. **人是一等泳道**：审批请求/决定都画在链上，人是唯一非会话参与者。
7. **结构模式（拓扑图）v1.1**；v1 只做过程视图。
8. **消息级定位不做**：点击只打开会话；行详情显示 `turn / step / seq` 锚点，不做精确滚动。
9. **因果文案**：事实栏「收到后它做了什么」，推断栏「可能由它引起」；不写「因此」。
10. **命名**：L2 事件 `task/supplemented`；工具 `pa_ticket_supplement`；动作值 `supplement`。

### 5.3 补充工具

```ts
// src/host/tools/pa_ticket_supplement/index.ts
pa_ticket_supplement({ ticketId, text, signalId? })
```

规则：

- `ticketId` 必须存在；`stage` 必须是 `running` 或 `blocked`；`workerSessionId` 必须存在且 agent 在线。
- `text` 非空，trim 后 ≤ 4000 字符（上限可调，别无限大）。
- 认领信号：与 `pa_task_route` 相同的回合边界逻辑；显式 signalId 不在本回合 → `invalid-signal`。
- 请求 id：`pa-supplement:${ticketId}:${sha256(text).slice(0,16)}`（幂等：同一条补充在 pending 时重复调用只投一次）；消息 id 由 `deliveryMessageId(requestId)` 得出。
- **先 steer 送达，再写账**：
  1. `task/supplemented`（`correlationId = ticketId`，`actor='router'`，`sessionId = router 会话`，payload 含 messageId）；
  2. 若认领了信号，再写 `decision/recorded { action:'supplement', signalId, ticketId }`。
- 失败码：`invalid-arguments` / `ticket-not-found` / `ticket-not-running` / `session-not-live` / `invalid-signal` / `delivery-failed`。错误信息要可行动（例：工单已结束 → 提示用 append/派发）。
- 工具描述要写清楚：**补充只用于给正在执行的工单加信息；新交付物用 dispatch/append**。

## 6. 详情推导（纯函数）

### 6.1 分层

- `src/host/projector/ticket-detail.ts`：**纯函数**，输入 = `{ ticket, ledger, sessions, now }`，输出 `TicketDetailResponse`。不读环境、不读文件。
- `src/host/sessions/session-window.ts`：读会话日志的适配层（live → `ctx.agents.get(id)?.session.snapshotEvents()`；cold → `readSessionEvents(ctx, id)`，内部先 `flush`），按窗口裁剪、上限 3000 条。
- `src/host/index.ts`：装配 + 缓存。

### 6.2 输入

```ts
interface TicketDetailInput {
  ticket: TicketView
  ledger: readonly L2Event[]
  /** 已按窗口裁剪的会话事件；queued 单可以为空。 */
  sessions: ReadonlyMap<string, readonly SessionEvent[]>
  now: number
}
```

### 6.3 步骤

1. **窗口**：`start = ticket.dispatchedAt ?? ticket.createdAt`；`end = ticket.endedAt ?? now`。追加单的历史必须被裁掉。
2. **mode**：扫 `task/queued`（ticketId）取 `mode`；`requestedBySessionId` 同处取。
3. **origin**：取最早一条 `decision/recorded`（`payload.ticketId = 本单` 且 `action` 是 `dispatch`/`append`，**排除 supplement**）→ signalId；再用 signalId 找 `signal/received`。没有决定（排队中）就只给 signal 或空。
4. **lane 集合**：
   - `router`（固定，从 requestedBySessionId 取会话）；
   - `human`：本单有 `approval/pending` 才加；
   - root worker：`ticket.workerSessionId`；
   - 子代理：root 日志里 `subagent/catalog` 的 `childId`，**加上**窗口内 `agent-message.senderSessionId` 出现过的已知子级（复用的旧子代理也要进）；带上祖先用于排序；`index` 按「人 → 负责人 → catalog 创建顺序」。
   - queued 单没有 worker lane。
5. **窗口内提取（L1）**：
   - `subagent/catalog` → spawn 行（from = parent，to = child，at = childCreatedAt，summary = 子级第一条 user/message 的文本或 catalog label/name，截 80 字）。**只有 `childCreatedAt ∈ 窗口` 才成行**；旧子代理在本单参与时只画它的 hop，不画旧 spawn 行；
   - `user/message` + `source.kind === 'agent-message'` → hop 行（from = senderSessionId，to = 会话；summary = 文本首行/前 120 字；text 全文 ≤ 4000；anchor 取 seq/turn/step）；
   - `user/message` + `source.kind === 'subagent-settled'` → 不画（v1）；lane 状态显示结束；
   - `turn/start` 计数与 open turn（判断 running lane）；
   - `assistant/message.usage` 累加 token；
   - 简报（`source.kind === 'dsh-personal-agent'` 且 messageId = `deliveryMessageId(ticketDeliveryRequestId(ticketId))`）→ 只作为 `dispatch/append` 行的 anchor，不单独成行。
6. **窗口内提取（L2，权威）**：
   - `task/queued` + `createdAt < dispatchedAt` → 排队里程碑（`ticketQueueBusy` / `ticketQueueCapacityFull`）；
   - `task/dispatched` → `dispatch`/`append` 行（from router，to worker，at dispatchedAt；mode 取 payload）；
   - `task/supplemented` → `supplement` 行（text、at、anchor.messageId）；
   - `approval/pending` → `approval` phase=request 行（from = `payload.requestedBySessionId`，to human；summary = question；详情展开显示 options/risk）；
   - `approval/decided` → phase=decision 行（from human，to = 对应 pending 的 `requestedBySessionId`；summary = 选择/答案；decision 字段）；
   - `approval/discarded` → 里程碑；
   - `task/interrupted`/`task/resumed` → 里程碑；
   - `task/reported` → **不单独成行**，只进交付卡（避免与链尾重复）；
   - `task/closed` → 终态里程碑（或 live 行的终点）。
7. **排序**：`at` 升序；同刻按 `source seq`，再按 lane index。行 id 稳定。
8. **扇出**：同一 parent、10s 内、连续的 spawn 行合并为 `fan` 行（只合并 spawn；agent-message 不合并）。`summary = "并行派发 ×N"`。
9. **live 行**（未结束）：有未决审批 → `human`，"等待你审批"；否则找窗口内最后 `turn/start` 无 `turn/end` 的会话 → 该 lane "正在第 N 轮"；否则 root "执行中"。
10. **指标**：`agents` = 执行会话数（不含 router/human）；`hops` = agent-message 行数；`supplements` = supplement 行数；`parallel` = 最大 fan 数；`pingPong` = 相邻 A→B 后紧跟 B→A（中间无其他消息）的次数；`turns` = Σ turn/start；`tokens` = Σ usage（`totalTokens ?? inputTokens + outputTokens + cacheReadTokens + cacheWriteTokens`，cache 缺省按 0；reasoning 已含在 output，不另加）；`durationMs = end - start`（已结束用 endedAt-createdAt 还是 dispatchedAt？统一 `end - start`，文档里写清楚）。
11. **completeness**：读日志失败/会话不存在 → `partial`/`unavailable` + reason；L2 行仍返回。

### 6.4 缓存与读日志

- `Map<ticketId, { signature: string; at: number; detail }>`；`signature = `${ledger.length}:${ticket.updatedAt}`}`；TTL 运行中 2s、结束 60s。`ledger.length` 变化即重算。
- 只对 `workerSessionId` 存在的单读日志；queued 单跳过。
- 先 `flush()` 再读；cold 会话用 `readSessionEvents`；单会话上限 3000 条，超出取尾部并在 completeness 标 `partial`。
- 读失败的会话不阻断整页；该 lane 标 `unknown`，`completeness.partial`。

### 6.5 失败降级

- 账本里有工单、日志不可读：只画 L2 行（排队/派发/审批/中断/汇报/关闭），链区顶部一行提示「会话日志不可读，仅显示账本事实」。
- 子代理日志缺失：该 lane 仍显示（catalog 有），hop 缺失。
- 时间回拨：`at` 可能乱序；排序后展示，不修改原值。

## 7. 页面实现规格

### 7.1 信息架构

### 7.2 行与交互

- 行是 `button`（整行可点、可聚焦）；rail 的 SVG 是 `aria-hidden` 装饰。**不要引入图形库或 canvas**：行是 HTML，弧线只是装饰，这样可测、可读屏、可 i18n。

- 悬停：1 行摘要 tooltip（用 primitives 的 Tooltip）。
- 键盘：Tab 聚焦、Enter 展开、Esc 收起。
- 新行：轮询增量；用户不在底部时显示「↓ N 条新投递」，不抢滚动。

## 10. 边界与风险

1. **追加窗口**：会话日志含上一单历史；必须 `start = dispatchedAt` 裁剪。L2 的 `createdAt` 到 `dispatchedAt` 之间是排队期，可以作为里程碑，但不要把上一单的 L1 行带进来。
2. **复用的旧子代理**：按「窗口内参与」进图，不按 `createdAt`；否则它的消息会指向不存在的 lane。
3. **日志不可读/已归档**：不要整页失败；返回 L2 行 + completeness。
4. **queued 单**：没有 workerSessionId；不要读日志、不要造 lane。
5. **补给的合法状态**：仅 running/blocked；ended → 提示用 append；queued → 还没执行。
6. **补给的副作用**：steer 可能起新回合；若工单阻塞在审批，页面并排显示「审批未决」与「收到补充」，不要暗示补充解决了审批。
7. **幂等**：supplement 的 requestId 用文本 hash；重复调用在 pending 时只投一次；L2 事件 eventId 幂等。
8. **事件顺序**：先送达、后记账；记账失败时消息已送达，日志会警告；不要让失败看起来像成功。
9. **时间**：`at` 可能同刻/回拨；稳定排序，不改原值。
10. **体积**：文本截断 4000；会话 3000 条；行数上限（比如 200）超出截断并标 partial。
11. **轮询**：详情 2s；不要在详情页再拉一次 snapshot；useSnapshot 共享。
12. **窄栏**：540px 无横向滚动；长名字/长文本 ellipsis；展开区内部滚动。
13. **i18n**：所有用户可见文案走字典；zh/en 同步；不要在组件里拼中文。
14. **样式**：复用宿主 token；只有 Agent 身份色是本地变量；不要自建通用设计变量。
15. **纯函数**：推导逻辑不要读环境；`deriveTicketDetail` 输入即全部事实。

## 12. 术语

- **派发 / append**：新/旧 worker 的新工单，排队（followup）。
- **补充 / supplement**：给当前工单插话（steer），不建单。
- **响应 / reply**：router 自己答复，不派单。
- **忽略**：来源层过滤，不是决定动作。
- **派单轨 / R 轨**：router 在图里的最左侧细轨。
- **回执**：工具返回、子代理完成通知；不是影响边。
- **投递**：Agent 主动发起、有接收方的信息。
- **窗口**：本单 `dispatchedAt → endedAt/now`；追加单必须裁剪。

## 与方案的差异（均为收窄，不改决策）
