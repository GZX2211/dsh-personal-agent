## 0. 本文定位

把「来源（感知）」与「事件页」两件事的实现方式一次定死，作为开发的唯一依据。凡是本文没有写到的行为，开发时不得自行发明；需要补充的，先回到本文更新。

三个已经排除的方向，写在这里避免返工：

| 排除项 | 原因 |
|---|---|
| 定时唤醒 Agent 去观察、再由它汇报给 Router | 二次传话、多一次模型调用、延迟不可控；语义判断也被放到了错误的一层 |
| 语义过滤（模型判断「值不值得报」） | 过滤只做代码层面的确定性事实判断；「要不要管」是 Router 的职责 |
| 由 Router 传 ID 才能完成事件归属 | 模型会漏传；归属是确定性层的责任 |

## 1. 范围

### 1.1 交付

1. **事件记录管道**：三类输入（用户消息 / 定时事件 / 感知事件）→ `signal/received`；Router 处理 → `decision/recorded`。
2. **感知运行时**：`host-event` / `fs-watch` / `script` 三种 Channel，声明式来源定义，确定性过滤，即时投递。
3. **Agent 面**：`perception-source` 内置 Skill + `pa_source_*` 工具 + Router 提示词补充。
4. **来源页**：感知来源列表、开关、线程开关、测试、删除；定时来源只读分区。
5. **事件页**：信号流水、结局展示、过滤与搜索。

### 1.2 不交付

- `client-event` / `webhook` / `http-poll` 三种 Channel（二期）。
- 来源的页面表单编辑（创建/编辑只走对话）。
- 语义过滤、事件优先级分级、静默时段、聚合窗口（`coalesce` 只留契约位）。
- 事件页的手动标记已处理、导出。

### 1.3 验收场景（三条，全部通过才算完成）

| # | 场景 | 期望 |
|---|---|---|
| A | 用户在 Router 说「帮我把 README 改一下」 | 事件页出现一条「用户消息」信号，结局「派发 #t-xxx」；点结局可跳工单 |
| B | 用户在 Router 闲聊一句「今天辛苦了」 | 事件页出现一条「用户消息」信号，结局「响应」 |
| C | 用户说「盯着 `D:\tmp\watchme.txt`，一改就告诉我」→ 改文件 → 关闭来源 → 再改文件 | ① 来源页出现「本地文件 · watchme」；② 第一次修改后 Router 收到感知消息并回复，事件页出现「感知」信号且结局为「响应」或「派发」；③ 关闭后再改文件，Router 无任何反应，事件页无新记录 |

补充验收：

| # | 场景 | 期望 |
|---|---|---|
| D | 用官方定时任务设置 1 分钟后提醒自己 | 事件页出现一条「定时」信号，带任务标题 |
| E | 一个 fs-watch 来源配两个线程，只触发其中一个的 match | 只产生该线程的信号；另一线程无记录 |
| F | 同一文件在同一秒内保存 3 次 | 只产生 1 条信号（去重） |

## 2. 设计前提（已确认的决策）

| # | 决策 | 结论 |
|---|---|---|
| 1 | 感知执行方式 | 事件驱动 + 代码确定性处理，零模型调用 |
| 2 | Channel 范围（MVP） | `host-event`、`fs-watch`、`script` |
| 3 | Router 忙时 | 默认排队（followup）；线程可标 `interrupt` 走 steer 插队 |
| 4 | 过滤表达力 | 线程开关 + match + 去重 + 最小间隔 + edge/level |
| 5 | 事件归属 | 处理类工具认领（显式 signalId 优先，否则 FIFO）；未认领一律 `reply` |
| 6 | 忽略 | 只发生在来源层（`delivered:false`），不产生 decision |
| 7 | 创建/编辑入口 | 对话创建（Skill + 工具）；页面只做开关/删除/测试 |
| 8 | 定时事件 | 复用官方 Schedule，只识别投递到 Router 的任务 |
| 9 | script 安全边界 | 接受「Router 可通过工具创建并常驻运行脚本」 |
| 10 | host-event 订阅面 | L2 账本事件 |
| 11 | 线程关闭 | 不产生、不记录 |

## 3. 概念模型

```
Channel  ── 怎样感知（host-event / fs-watch / script；未来由插件注册）
   │
   ▼  raw event
Candidate ─ 一条候选事实：{ thread, statement, externalId?, at?, state?, meta? }
   │
   ▼  Filter（纯函数，确定性）
Signal   ─ 事件层的一条输入记录：signal/received
   │        delivered=false → 被过滤（记录 rule）
   │        delivered=true  → 已投递进 Router inbox
   ▼
Decision ─ Router 的处理结果：dispatch / append / reply
```

术语表：

| 术语 | 定义 |
|---|---|
| **来源（Source）** | 一个可开关的感知单元，内含一个 Channel 实例与 N 条线程 |
| **线程（Thread）** | 来源内的一类感知事件，承载 match / 去重 / 节流 / edge 规则 |
| **候选（Candidate）** | Channel 产出、尚未经过滤的一条事实 |
| **信号（Signal）** | 过滤判定后写入 L2 的一条事件层记录，是事件页的最小单元 |
| **认领（Claim）** | 处理类工具把某一个信号与自己的动作绑定 |
| **决定（Decision）** | 一次处理的结果；一条决定对应一个信号 |
| **处理类工具** | 执行时可能「处理」信号的工具（目前只有 `pa_task_route`） |

`source/updated` 承载定义变更、来源开关、线程开关三种情况——投影只折叠最后一条，不区分变更种类。

**`L2Event` 联合**追加三种事件类型。

**`correlationId` 约定**：

- `signal/received` 与对应的 `decision/recorded` 都用 `signalId` 作为 `correlationId`，事件页据此聚合。
- `source/*` 用 `sourceId` 作为 `correlationId`。
- 工单事件沿用 `ticketId`。

**幂等键**（沿用 `deriveEventId`）：signal 的 `correlationId` 即 `signalId`，因此同一信号重复产生只入账一次。

### 4.2 新增 `src/shared/sources.ts`

```ts
export const CHANNEL_KINDS = ['host-event', 'fs-watch', 'script'] as const

export const FS_EVENT_KINDS = ['add', 'change', 'unlink'] as const

export type MatchValue = string | number | boolean | (string | number)[]

/** 确定性匹配表达式；`path` 支持 `payload.outcome` 这类点路径。 */
```

### 4.5 投影（`src/host/projector/project.ts`）

新增两个累加器：

- `signals: Map<signalId, SignalAccumulator>`：由 `signal/received` 建立，由 `decision/recorded` 补充 `decision`。
- `sources: Map<sourceId, SourceAccumulator>`：由 `source/created|updated|removed` 折叠出 `{ definition, removed }`。

排序与截断：

- 信号按 `receivedAt` 倒序（同时间按 `signalId` 倒序），只保留最近 **500** 条进入投影，避免快照无限增大；完整历史仍在账本里。
- 来源按 `createdAt` 升序。
- 来源的 `deliveredCount` / `filteredCount` / `lastEventAt` 从信号集按 `sourceId` 聚合；`threadId` 同理。
- 运行时状态（`status`/`lastError`）不在投影里，由 `PerceptionService` 提供，快照组装时合并。

新增纯函数 `projectSignals` 与 `projectSources`，由 `project()` 调用；保持「输入即全部事实」。

### 5.2 装配与启动顺序

```
插件 mount
→ 打开账本 / kv（现有）
→ Scheduler、Decorator、WorkerObserver（现有）
→ SignalService 创建（identity + ClaimRegistry）
→ 注册 Router inbox 观察者（需要 routerSessionId，可延后到就绪）
→ PerceptionService 创建（依赖 store / kv / 投递 / 信号记录 / router 身份）
→ router 会话就绪后：
    → 从投影还原来源定义
    → 启动 enabled 的 Channel
→ 注册内置 Skill（perception-source）
→ HTTP 面挂载（现有 + 新路由）
```

注意：`PerceptionService` 必须在 Router 会话身份确定之后才能启动投递能力；来源还原与 Channel 启动放在 `ensureRouterSession` 之后。

### 5.3 错误与降级

| 场景 | 行为 |
|---|---|
| 单个 Channel 启动失败 | 该来源 `status='error'`，记录 `lastError`；不影响其他来源与宿主；来源页可见「重启」 |
| Channel 运行期异常 | 捕获并记日志；`script` 按重启策略退避；`fs-watch` 重新挂载（最多 3 次），仍失败则 `error` |
| 投递时 Router 会话不可用 | 记日志，信号**不落账**（不产生假事实）；来源 `lastError` 记录 |
| 账本 append 失败 | 沿用现有 `EventStore` 的故障语义：拒绝后续写入，日志暴露 |
| 定时来源读取失败 | `timers` 降级为空数组，不影响快照其余部分 |
| 脚本输出非法行 | 丢弃该行并记日志，计入 `lastError`；连续 20 行非法则视为脚本异常并走重启策略 |

## 6. 关键机制

### 6.1 信号识别（三类来源）

`src/host/signals/observer.ts` 订阅全局 `session/event`，只处理 Router 会话：

| L1 事件 | 处理 |
|---|---|
| `agent/inbox/spliced` | `inserted.length > 0` 时逐条识别；`removedCount > 0` 或 `outcome === 'canceled'` 一律忽略 |
| `agent/inbox/claimed` | 建立 `messageId → { signalId, turn }` 关联，交给 ClaimRegistry（不落账） |
| `turn/end` | 触发该 turn 的信号结算（见 §6.3） |

分类规则（**白名单**，其余一切 source 一律忽略）：

| `source.kind` | 信号类型 | 附加字段 |
|---|---|---|
| `user` | `user-message` | `text` = 消息文本截断 500 字 |
| `schedule` | `timer` | `sourceId` = 正文 `schedule_id_json`；`text` = `reminder_prompt_json`；`sourceName` 由快照组装时反查任务标题 |
| `dsh-personal-agent/perception` | `perception` | `sourceId`/`threadId` 取自消息 source 的附加字段；`text` = 正文事实行 |
| 缺失 `source` | 不识别 | 日志中存在无 source 的注入消息（coordinator 等），必须容错 |
| 其他（`agent-instructions` / `subagent-settled` / `team-message` / `agent-message` / `tool-jobs` / `plugin` / `coordinator` / `goal` / `subagent-report` / `user-approval` / `dsh-superagent` / `repeat-tool-reminder` / `working-directory` / `dsh-personal-agent` 的 relay） | 不识别 | — |

**实测依据**（见 `collab/md/探针结果-感知与事件.md`）：

- `source` 整体 JSON 持久化，自定义字段与嵌套数组都保留（已用多种生产者的真实样本确认），因此感知消息可以在 `source` 上直接带 `sourceId`/`threadId`；正文「信号：」行保留为兜底。
- `agent/inbox/claimed` 在 556 个日志文件中出现 0 次，确认不落盘，必须运行时订阅并当场记账。
- `spliced` 先于 `turn/start` 落盘，所以归属必须靠运行时 claimed 的 `turn`，不能靠 seq 区间推断。

`signalId` 派生：

```
已投递：s- + sha256("m:" + sessionId + ":" + messageId).slice(0, 10)
被过滤：s- + sha256("f:" + sourceId + ":" + threadId + ":" + externalId).slice(0, 10)
```

同一条消息被重复投递（重启重放）时 `signalId` 相同，`deriveEventId` 幂等，不会重复入账。

### 6.2 投递

```ts
async function deliver(signal: PendingSignal): Promise<void> {
  const agent = await resolveRouterAgent()          // resolveAgent；无 live agent 则抛 DeliveryError
  const message = createPerceptionMessage(signal)   // id = `pa-perception:<signalId>`
  if (signal.interrupt) agent.steer(message)
  else agent.followup(message)
  await ctx.sessionPersistence.flush()
  store.append({ type: 'signal/received', actor: 'system', correlationId: signal.signalId, payload })
}
```

**顺序：先投递、后记账。** 理由：账本记录的事实是「已进入 Router inbox」，投递成功才能成立；投递失败时不产生记录，不会出现「账本有、inbox 无」的假事实。这与工单的「先存后做」不冲突——那里副作用的对象是外部世界，这里副作用的对象是宿主自己的 inbox。

**消息格式**（正文只陈述事实，不带任何行动指令）：

```
[感知事件]
来源：{sourceName} · {threadName}
时间：{YYYY-MM-DD HH:mm:ss}
事实：{statement}
信号：{signalId}
```

`createPerceptionMessage` 的 `source` 声明为 `{ kind: 'dsh-personal-agent/perception', form: 'notice', sourceId, threadId }`，与现有 `dsh-personal-agent` relay 的做法一致；即使附加字段在持久化时被裁剪，正文里的「信号」行也能兜底关联。

**被过滤的信号**：不投递，直接 `store.append({ delivered: false, rule })`。

**合并（`coalesce`）**：本轮不实现，仅在 `ThreadDefinition` 中保留契约位。默认逐条立即投递。

### 6.3 认领与结算

**ClaimRegistry**（进程内）：

```ts
interface ClaimRegistry {
  /** inbox/claimed 时登记：消息属于哪个 turn。 */
  onClaimed(messageId: string, turn: number): void
  /** 处理类工具调用时认领一条信号；返回被认领的 signalId。 */
  claim(sessionId: string, explicitSignalId?: string): string | undefined
  /** turn 结束时取出未认领的信号并清空该 turn。 */
  settle(turn: number): string[]
}
```

数据：`pendingByTurn: Map<turn, signalId[]>`、`claimed: Set<signalId>`。

**`pa_task_route` 的认领流程**：

1. 解析参数，若带 `signalId` 则校验其存在且未结算；
2. 取当前 turn：`ctx.agents.turnBoundaryOf(session).lastTurn`（`ToolRunContext` 不含 turn 字段，已实测）；
3. 调 `ClaimRegistry.claim(turn, explicitSignalId)`：显式优先，否则取该 turn 最早的未认领信号（FIFO）；
4. 写 `task/queued`（既有行为）；
5. 若有信号被认领，写 `decision/recorded { action, signalId, ticketId }`；
6. 工具返回值里追加 `signalId`，让 Router 知道这次动作关联了哪条信号。

**turn/end 结算**（`sessions/observer.ts`，Router 会话）：

- `settle(turn)` 取出未认领的 signalId；
- 逐条写 `decision/recorded { action: 'reply', signalId, inferred: true }`；
- 不检查 assistant 文本：未认领就一律是响应（未来外发消息这类动作不调 `pa_task_route`，也天然落在响应里）。

**重启**：ClaimRegistry 是内存态，重启丢失。已投递但未结算的信号会停在「待处理」，事件页如实显示；不做自动收口（后续可加超时策略）。

**多事件同 turn**：

| 情况 | 行为 |
|---|---|
| N 条未认领信号 + N 个处理动作 | FIFO 一一配对 |
| N 条信号 + M 个动作，M < N | 前 M 条按 FIFO 绑定，其余在 turn/end 结算为 reply |
| N 条信号 + M 个动作，M > N | 多余动作不绑定信号（只产生工单） |
| 需要跨序精确对应 | Router 显式传 `signalId`（消息正文里有） |

### 6.4 过滤

`src/host/perception/filter.ts` 是纯函数：

```ts
export type FilterVerdict =
  | { action: 'drop'; reason: 'thread-disabled' }
  | { action: 'filtered'; rule: 'match' | 'min-gap' | 'no-change' }
  | { action: 'deliver' }

export function judge(input: JudgeInput): FilterVerdict
```

判定顺序：

1. **线程不存在或未启用** → `drop`，**不记录**（线程关了就当它不存在）。
2. **match 不通过** → `filtered('match')`，记录。
3. **去重命中**（`dedupe` 键已在 seen 集合） → `drop`，**不记录**（同一事实已经记录过，重复到达不是新事实）。
4. **节流**（`now - lastDeliveredAt < minGapSec`） → `filtered('min-gap')`，记录。
5. **edge 模式且状态未变化** → `filtered('no-change')`，记录；状态变化则更新 kv 状态后投递。
6. 其余 → `deliver`。

`seen` 集合从投影重建（启动时扫描 L2 信号的 `sourceId + threadId + externalId`，取最近 10 000 条）；运行期每投递一条就加入。

**edge 状态**：`Candidate.state` 必须由 Channel 提供；缺失时记录一条警告并退化为 `level`（每次都投递）。

kv 键：

```
perception/<sourceId>/<threadId>/last-delivered   # epoch ms
perception/<sourceId>/<threadId>/edge-state       # 上次状态字符串
```

### 6.5 Channel：host-event

订阅 `EventStore` 的新增事件（`subscribe` 在 `append` 成功后同步回调，回调内部只做入队与过滤，不重入 append）。

配置：

```json
{
  "kind": "host-event",
  "subscriptions": [
    {
      "event": "task/closed",
      "thread": "tickets",
      "statement": "工单 {payload.ticketId} 以 {payload.outcome} 结束"
    },
    {
      "event": "approval/pending",
      "thread": "approvals",
      "statement": "出现待审批：{payload.question}"
    }
  ]
}
```

- 只为 `subscriptions` 里声明的事件类型回调；`signal/received` 与 `source/*` 一律排除，防止自我感知。
- `statement` 用点路径插值（`{payload.ticketId}`、`{type}`、`{time}`），取不到值时渲染为空字符串。
- `externalId` = 该事件自身的 `eventId` —— 天然去重。
- `state` = `eventId`（edge 模式下不会误判）。
- 回调是同步的：入队后由微任务处理，避免阻塞账本写入。

### 6.6 Channel：fs-watch

配置：

```json
{
  "kind": "fs-watch",
  "paths": ["D:\\proj\\src"],
  "recursive": true,
  "events": ["add", "change", "unlink"],
  "ignore": ["**/node_modules/**", "**/.git/**", "**/*.tmp", "**/~$*"],
  "debounceMs": 300,
  "statement": "{event} {path}"
}
```

- 每个路径一个 `fs.watch(path, { recursive })`；同一个路径在 `debounceMs` 内的多次事件合并为一次。
- `ignore` 用自实现的 glob→RegExp（支持 `**`、`*`、`?`，`/` 与 `\` 等价），不引入依赖。
- `add`/`change` 用 `statSync` 取 `mtimeMs` 与 `size`，`externalId = "<path>:<mtimeMs>:<size>"`；`unlink` 用时间戳。
- `statement` 插值变量：`{event}`、`{path}`、`{name}`、`{dir}`。
- `state` = `mtimeMs`（edge 模式用）。
- 路径不存在时 Channel 启动失败，来源标记 `error`（创建时即校验）。

### 6.7 Channel：script

配置：

```json
{
  "kind": "script",
  "command": "pwsh",
  "args": ["-NoProfile", "-File", "<abs>/watch.ps1"],
  "cwd": "D:\\proj",
  "restart": "on-failure",
  "scriptPath": "perception/src-abc123/watch.ps1",
  "scriptHash": "…"
}
```

- **脚本正文由 `pa_source_create` 的参数传入**，Host 校验后写入 `<state>/perception/<sourceId>/<scriptName>`，再以 hash 形式记入来源定义。选这条路径的原因：Router 被 `ROUTER_DENY` 裁掉了 `write`/`pwsh`，它自己写不了文件也跑不了命令。
- 启动前读取文件并比对 `scriptHash`；不一致时**以文件为准**（视为用户手改），自动写一条 `source/updated` 同步 hash，并记日志。
- 输出协议：stdout 每行一个 JSON：

```json
{"thread":"changes","statement":"配置文件被修改：app.yml","externalId":"app.yml:1732","at":1732000000000,"state":"mtime:1732"}
```

  必填 `thread` 与 `statement`；`externalId` 缺省用 `statement` 的 hash；`at` 缺省取到达时间。
- stderr 进插件日志。单行超 16 KiB 截断。
- 速率限制：每秒最多 100 行，超出丢弃并记日志（防止脚本失控刷屏）。
- 退出与重启：`on-failure` 时指数退避（1s→2s→4s→…→60s），连续 10 次失败后标记 `error` 并停止；`never` 不重启。
- 停止：`child.kill()`；5 秒未退出则强杀。Windows 上用 `taskkill /T /F` 清理进程树（在 `spawn` 时记录 pid）。
- 插件卸载时停止全部脚本进程。

### 6.8 来源热生效与开关

| 操作 | 顺序 |
|---|---|
| 创建 | 校验 → 写 `source/created` → 启动 Channel → 返回 `SourceView` |
| 更新 | 校验 → 停旧 Channel → 写 `source/updated` → 启动新 Channel |
| 开关 | 同上；`enabled=false` 时只停不启 |
| 删除 | 停 Channel → 写 `source/removed` → 保留脚本文件（便于审计） |

启动失败不回滚账本事实（事实不可撤回），来源保持 `enabled` 但 `status='error'`，页面提供「重启」；重启即重新走启动流程。

### 6.9 幂等与重放

| 场景 | 处理 |
|---|---|
| 同一消息重复投递 | `signalId` 由 `messageId` 派生，`deriveEventId` 幂等 |
| 同一候选重复到达（externalId 相同） | 去重命中，不记录 |
| 同一事实被过滤后再次到达 | `signalId` 由 externalId 派生，幂等 |
| 账本重放 | 投影重算，去重集合与来源定义从投影重建 |
| 进程重启 | 已投递未结算的信号保持「待处理」；来源从投影恢复并重新启动 |

### 6.10 定时事件接入

- 不创建、不修改官方任务；只识别 `source.kind === 'schedule'` 的 inbox 消息。
- 正文解析（实测两种固定文本变体，字段前缀一致）：
  ```
  [SCHEDULE REMINDER]
  <说明行：Present reminder_prompt_json … 或 This is a scheduled message from the user>
  schedule_id_json: "schedule-…"
  occurrence_at: 2026-09-29T02:42:51.334Z
  reminder_prompt_json: "…（换行已 JSON 转义）"
  ```
  按行前缀取冒号后的剩余部分做 `JSON.parse`；`reminder_prompt_json` 在 JSONL 行内不含真实换行。解析失败时 `sourceId` 留空，`text` 取正文首行。
- 来源页的定时分区由 `ctx.schedule.catalog()` 提供，过滤 `target.kind==='session' && target.sessionId===routerSessionId`；只读，不做暂停/恢复（避免与官方存储双写）。

8. **创建后必须告诉用户**：来源名称、监控什么、触发条件、如何关闭（去来源页）。

### 14.3 §6.1 幂等键修正（实现事实）

`signal/received` 与 `decision/recorded` 的 `eventId` **只由 `signalId` 派生**，`receivedAt`、`text` 等观测细节不参与（`host/store/event-id.ts` 的 `KEY_FIELDS`）。

原因：同一条消息被再次观察时 `receivedAt` 必然不同，若它参与身份，「同一消息重复观察只入账一次」的承诺就不成立。这一条修正了 §6.1 末尾的幂等表述。

`signalId` 的材料编码用 JSON 数组（`["m", sessionId, messageId]`）而不是冒号拼接：插件自己投递的消息 id 形如 `pa-delivery:<requestId>`，拼接会让不同输入落到同一个 id。

### 14.4 §6.3 认领与结算的细化（已确认）

- **显式 signalId 必须落在本回合**：不在本回合的待认领列表里（抄错、跨回合、已被认领、回合尚未开始）一律抛 `invalid-signal`，工具调用失败。绑错信号比报错更难发现。
- **认领发生在任何账本写入之前**：指认无效时不会留下一条来源不明的工单。
- **任何 `turn/end` 都结算**：`completed` / `aborted` / `error` / `max-tokens` / `blocked` / `forked` 一律把未认领信号结算为 `reply`。回合一旦关闭就不会再有处理动作，悬着只会让事件页永远停在待处理。
- **非 `completed` 时记 `reason`**：`decision.reason` 写入结束种类（如 `aborted`），账本因此能区分「正常闲聊」与「当时被打断」。

### 14.5 §4.5 投影口径（已确认）

- 视图上限改为 **200** 条（`SIGNAL_VIEW_LIMIT`，从方案的 500 调整）。
- `stats.signals` 按**全量**账本信号统计，不随视图截断：历史事实不因展示上限而消失。
- 事件页的搜索需要检索 200 条之外的历史，因此 P3 需要一个读全量账本的查询入口（HTTP 查询端点），不能只靠快照。这一点在 P3 落地时补契约。

### 14.6 §6.10 定时正文解析（实现事实）

只解析 `schedule_id_json` 与 `reminder_prompt_json` 两个字段。`occurrence_at` 的值在实测样本里是**未加引号的 ISO 时间**，不是合法 JSON，本方案也不需要它，因此不解析。

### 14.7 P1 接缝约定（重要）

**感知消息由 observer 统一记账，投递方不再写 `signal/received`。**

原因：若投递方先算 signalId 再投递，而 observer 又按 `messageId` 派生一次，两边会得到不同的 id，一条感知就会变成两条信号。统一到「观察者记账」后：

- 一类输入只有一个记账点（用户消息、定时消息、感知消息都一样）。
- 投递失败时不会产生信号——`followup` 成功才会有 inbox splice，账本因此只记「确实进入过 inbox」的事实，与 §6.2 的语义一致。
- signalId 一律由 `deliveredSignalId(sessionId, messageId)` 派生；P1 只需保证感知消息的 `messageId` 稳定（由来源坐标派生），不需要预先知道 signalId。

P1 实施时按此调整 §6.2 的 `deliver`：投递成功只 `flush`，不再 append。

### 16.2 来源操作契约（实现事实）

```ts
POST   /personal-agent/api/sources/:id/toggle   body: { enabled, threadId? }
POST   /personal-agent/api/sources/:id/test     body: { waitMs? }（可省略）
DELETE /personal-agent/api/sources/:id
GET    /personal-agent/api/signals?q=&limit=
```

- 响应体：`{ ok: true, source }` / `{ ok: true, signals }` / `{ ok: true, removed }` / `{ ok: true, signals, total }`。
- `threadId` 缺省时切整个来源；提供了就只切那一条线程（整体替换该线程的定义）。
- 开关是幂等的：同一个状态重复提交不写账本。
- **「重启」复用 toggle**：对一个 `enabled=true` 但未运行（`status='error'` 或没有运行体）的来源再次提交 `enabled=true`，会停旧渠道并重新启动；这不写账本（定义没变）。来源页错误态因此不需要额外接口。
- 失败映射：`source-not-found` → 404，`source-invalid` → 400，`source-start-failed` → 502，其余 → 500 `internal`（`host/console-api/errors.ts`）。
- 协议层收窄请求体：`enabled` 必须是布尔，`threadId` 必须是字符串，`waitMs` 必须是有限数字；不合法直接 400，不进入服务。

### 16.3 `SourceConfigView`（补充 §4.3）

```ts
export type SourceConfigView =
  | { kind: 'host-event'; events: string[] }
  | { kind: 'fs-watch'; paths: string[]; recursive: boolean; debounceMs?: number }
  | { kind: 'script'; command: string }
```

- 只带「在盯什么」：host-event 的事件类型去重；fs-watch 的路径与递归标志；script 只给命令。
- 不带脚本正文、脚本哈希与 ignore 模式——它们对解释来源没有帮助，还会把定义全文塞进每次轮询。

### 16.4 事件页历史检索（补充 §14.5）

- 信号投影拆成两件事：`project()` 取最近 `SIGNAL_VIEW_LIMIT` 条进快照；`projectSignals(events)`（`host/projector/project.ts`）返回全量。
- 两者共用 `signal-query.ts` 的折叠规则（`applySignalEvent` / `toSignalViews`），结局与去重口径不会走散。
- `querySignals(views, { q, limit })`：匹配 `text` / `sourceName` / `threadName`，空白分词 AND；`total` 是全量匹配数，`signals` 最多 `limit` 条。
- 条数范围 `SIGNAL_QUERY_LIMIT = { min: 1, max: 500, default: 200 }`；越界与非有限值由 `clampSignalLimit` 收敛。
- 事件页搜索输入非空时走该端点（250ms 防抖）；为空时直接用快照那一段。轮询快照的可见变化会触发重查。

### 16.5 `service.test` 语义（实现事实）

- 来源不存在 → `source-not-found`；来源已关闭 → `source-invalid`（先打开再测试）；启动失败 → `source-start-failed`。
- fs-watch：向运行体注入一条合成候选，候选照常走 match / 去重 / 投递，陈述加 `[test]` 前缀；`externalId` 用 `test:<path>:<now>`，不与真实事件撞去重。
- script：停旧渠道并重启，等 `waitMs`（默认 1500ms，上限 5000ms）后收集输出。
- host-event：不主动触发，只返回最近信号。
- 返回值是该来源最近 5 条信号（按投影倒序）：测试要回答「这一下有没有通」，不是查历史。
- 测试是**真实投递**：Router 会收到一条感知消息，事件页也会出现对应信号（用户已确认）。

### 16.6 页面结构与交互

来源页（`views/Sources.tsx` + `SourceCard` / `ThreadRow` / `TimerCard`）：

- 说明条 + 「感知来源」分区 + 「定时来源」分区；两段各有自己的空态。
- 来源卡片折叠时：名称、状态点与状态词、渠道徽标、线程数、最近触发（悬停显示「最近触发」标签）、来源开关。
- 展开后：线程开关与计数、配置摘要（路径/事件/命令）、`lastError`、测试/重启/删除；测试结果显示在展开区（紧凑信号卡片）。
- 开关与线程开关乐观更新，失败回滚（清掉覆盖即回到快照值）并弹 Toast；删除用官方 `Modal` 二次确认。
- 「在对话中创建」聚焦 `snapshot.routerSessionId`；该字段缺失时按钮禁用。
- 定时分区只读：标题、已启用/已暂停、节奏摘要、已投递数、下次触发；「打开自动化任务」= `ctx.layout.selectPanel('schedules')`。

事件页（`views/Events.tsx` + `SignalCard`）：

- 胶囊：全部 / 用户 / 定时 / 感知 / 已过滤；搜索框复用 `FilterBar`。
- 卡片：类型徽标、来源行（用户消息显示「对话」）、相对时间（悬停绝对时间）、事实文本（最多 3 行）、结局徽标、推断标记（悬停解释）。
- 结局为派发/追加且带工单时是按钮：切到工单标签，以工单短码作为工单页的初始搜索词（页面用 key 重挂载）。
- 空态区分「检索中」「搜索没命中」「这一类还没有」。

### 16.7 组件与样式

- 一律复用官方原子：`Switch`、`StateDot`、`Tag`、`Tooltip`、`Modal`、`Toast`、`Button`、`Pill`、`Input`、`AnimatedRows`；自建的只有卡片骨架（`.pa-signal`、`.pa-source__*`、`.pa-thread`）与分区骨架（`.pa-page`、`.pa-section*`）。
- 状态色全部取主题 token；新增类只放在 `style.ts`，不新造设计变量。
- 定时节奏、时长与周几用 `Intl`（`NumberFormat` unit / `ListFormat` / `RelativeTimeFormat`）本地化；界面文案全部走词典。
- `Translate` 扩展为 `(key, params?) => string`：带占位符的文案（`线程 {count}`、`共 {count} 条`）由词典模板填充，缺参时保留占位符而不是变成空白。

### 16.9 来源页调整（依据 2026-11-20 页面批注）

| 项 | 调整 |

| 说明条 | 不再可见，移入工具栏右侧的问号对话框（`helpBodySources` + `helpBodySourcesSearch`） |
| 分区标题 | 删除「感知来源」标题与「定时来源」整个分区 |
| 创建入口 | 「在对话中创建」移到工具栏左侧，与列表左边缘对齐（`FilterBar` 新增可选 `leading`） |

### 16.11 工单页排序（依据 2026-11-20 页面批注）

工单页列表改为「最新更新的在最上面」：
