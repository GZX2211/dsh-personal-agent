本文档说明本项目的核心架构、设计意图与关键取舍。

---

## 1. 问题与定位

DSH 本体把每个会话做成独立的 append-only 事件日志（L1），会话之间完全隔离、没有共享状态通道；`ctx.emit` 是进程内同步广播，不持久也不可重放；官方审批的 pending 不持久、无恢复令牌。于是跨会话的任务状态、需要人放行的审批门禁、以及「状态不经 Router 转述直接可见」这三件事，本体都不提供。

**dsh-personal-agent** 的回应是：在概率层（Router 与 Worker 两个模型会话）之间插入一个自建的**确定性事件层（L2 账本）**。所有状态归属权在中间层，两端只提交事实与消费决定；Router 只做意图理解、派发与按需 pull 查询，Worker 在隔离会话里执行，审批由总控台直接呈现给人。V0 架构设计稿把它概括为一句话——把审批与任务状态从概率层上提到确定性层，总控台是该层的投影与过滤器。

项目追求的是**降低人的注意力消耗**（一个窗口对话、状态自己可见、审批集中处理），不追求长期记忆与用户画像、多 Router / 跨进程、按成员配置能力，也不自建工具管理体系。

## 2. 核心架构

```text
┌─ 概率层 ─────────────────────────────────────────────┐
│  Router 会话             Worker 会话（每个工单一个）    │
│  意图理解 / 派单 / 查账     执行 / 提交审批              │
└──────┬───────────────────────┬───────────────────────┘
       │ 领域工具提交事实       │ 提交审批 / 汇报
       ▼                       ▼
┌─ 确定性层 · L2 账本（append-only，唯一事实源） ────────┐
│  events.jsonl ──纯函数投影──▶ 工单 / 审批 / 调用链视图   │
│  Dispatcher/Scheduler：计划 → 建会话 → 投递             │
│  Perception：来源定义 → 过滤去重 → 投递进 Router inbox   │
└──────┬────────────────────────────────────────────────┘
       │ 同源 HTTP 面 /snapshot
       ▼
┌─ 表现层 ─────────────────────────────────────────────┐
│  右侧栏「总控台」：概览 / 审批 / 工单 / 事件 / 来源 / 设置 │
│  状态自己可见（不经 Router）· 人在此点审批               │
└───────────────────────────────────────────────────────┘
```

### 2.1 事件溯源与派生状态

账本（`/store/event-store.ts`）是 append-only 的 `events.jsonl`：写入顺序固定为「分配 seq → 写盘 fsync → 改内存」，失败时回滚文件长度；`eventId` 由关键字段派生实现幂等。工单与审批**都没有 status 字段**——阶段由 `projector/project.ts` 从事件序列现算，`blocked` 只是 `running` 的副标签。这样状态永不与账本冲突，且阶段由事件顺序而非墙钟决定。

### 2.2 双向协作的调度与会话

`dispatcher/` 与 `sessions/`、`approvals/` 与 `sessions/` 是双向协作：调度与审批调用会话去执行与投递，会话在回合边界回调调度器或登记阻塞。两侧只通过注入的实例与 `context.ts` 声明的服务面互相作用，不读对方内部状态——这是协作关系，不是分层倒置。Scheduler 每轮只执行第一个动作、失败即停，避免异常数据导致无限自转。

### 2.3 审批门禁与自愈

Worker 调用 `pa_approval_submit` 后阻塞等待人的决定，`ResolverRegistry` 登记一个 pending resolver。人提交时走三条支路：目标会话已归档则写作废；resolver 仍阻塞则 inline 送达并等确认；agent 已停止则 followup 投递唤醒。三者都遵循**先送达、后记账**。启动时 `healPendingApprovals` 从会话日志的 `tool/result` 元数据里找回已送达但未记账的决定，补写 `recovered:true`。

### 2.4 感知来源

来源定义（渠道 + 线程 + 声明）随 `source/*` 事件入账，运行时状态只在内存。三类渠道：`host-event`（订阅内部事件，排除自身产生的信号避免自触发）、`fs-watch`（本地文件变化）、`script`（外部协议通用适配，脚本落盘并做哈希复核、限流与失败退避）。过滤顺序为线程开关 → match → 去重 → 最小间隔 → 边沿判定，投递与记账分离。

### 2.5 只读概览读模型

`runtime/` 只读账本与会话内存，派生 Worker 状态、上下文占用与近 7 天活动，不写账本、不反向依赖 `sessions/`。它不写账本，每个组件失败各自降级，不影响主链路。

### 2.6 三层依赖方向

- `shared/` 是纯契约层：禁止运行时 import，不含全局可变状态、单例或副作用，可被两端零风险引用。
- `host/` 内部靠显式注入实例协作，模块级单例与 import 根入口都被禁止；根 `index.ts` 是唯一装配点。
- `client/` 依赖单向：`components / hooks → lib`，`lib` 不反向依赖；网络只经统一边界与注入面。

## 3. 关键设计取舍

| 设计选择 | 主要收益 | 需要承担的代价 |
| --- | --- | --- |
| 事件溯源 + 纯函数投影，状态不存 status | 状态永不与账本冲突、可重放、天然幂等、抗时钟回拨 | 每次投影需折叠事件（靠投影缓存缓解）；新增字段要保持旧账本可读，写入纪律严格 |
| 「先送达、后记账」+ 启动自愈 | 不会出现「账本说已决定但 worker 从未收到」的不一致 | 引入 deliver/acknowledge/cancel 三态同步复杂度，以及靠 `presentationMeta` 持久化决定的耦合 |
| 信号配对只存内存（ClaimRegistry） | 配对是运行时事实，实现简单，不污染账本 | 重启即丢失，未结算信号停在待处理，不自动收口 |
| 投递幂等限于本进程 | 无需扫持久化历史，简单高效 | 重启后同一 requestId 会再投一次，重复窗口靠「先送达后记账 + 自愈」压小 |
| Router 被裁掉动手工具，只给派单与查询 | 职责边界清晰，技术工作隔离到工单会话 | Router 完全依赖 Worker，执行会话的任何问题都要走派发 / 补充路径 |
| 三类内置渠道 + script 通用出口 | 覆盖本地文件、内部事件与外部服务，判断权留给 Router | script 需落盘、进程管理、指数退避重启与限流，实现较重 |
| 来源运行时状态不落账 | 账本纯净，「曾经运行过」这种不可回放事实不入账 | 重启后状态重置，需重建渠道并按文件同步脚本哈希 |

这些取舍不意味着某种方案绝对更优，而是围绕「注意力预算与事实可回放」做出的可配置平衡；具体阈值与行为以代码和测试为准。

## 4. 架构不变量

以下约束界定架构边界，也是 [贡献指南](CONTRIBUTING.md)「项目边界」的引用源。

1. **账本是唯一事实来源。** 状态由事件序列派生，工单与审批不存 status 字段；写入只追加、按内容派生幂等键。
2. **依赖单向。** `shared/` 禁止运行时 import；`host/` 模块不得 import 根入口；`runtime/` 不反向依赖 `sessions/`；`console-api/` 不直接读写账本。
3. **状态单一所有权。** 每个事实只有一个所有者与一个写入边界，状态变化只经语义化操作，禁止直接改字段或跨模块改内部状态。
4. **纯函数与副作用分离。** 判定、归一化、投影、签名与键推导、字段映射必须是纯函数；数据「传入即全部事实」，不隐式读取全局或环境。
5. **先送达、后记账。** 审批决定、补充投递、感知投递都在确认副作用成功后才写账本；认领动作早于任何账本写入。
6. **根是唯一装配点。** 有状态模块由根 `index.ts` 装配，模块间通过显式注入的实例与接口协作，不引入模块级单例。
7. **契约兼容优先。** 新增字段默认可选，删除或改义给兼容路径，退役字段只保留读取兼容、禁止新增写入；行为变化必须显式记录。

以上约束用于界定架构边界与评估设计变更。具体实现以代码和测试为准。
