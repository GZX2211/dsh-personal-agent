# Test Module Rules

## 范围与目标

适用于 `tests/`。测试用于验证真实行为、稳定契约、模块协作和完整流程，而非提高覆盖率数字。

本文件是**测试侧唯一权威**：测试的层级选择、文件命名、编写规则与覆盖率要求只在本文件出现一次。

## 层级与选择
- `tests/client/`、`tests/host/`、`tests/shared/`：单元测试。
- `tests/integration/`：集成测试。验证多模块协作。可用受控基础设施，但不得全量 Mock 内部模块。

选择能最低成本验证目标行为的最低测试层级。不得为数量把真实协作全部 Mock 成 Unit。

## 文件与命名
- `tests/client/`、`tests/host/`、`tests/shared/` 必须镜像对应 `src/` 目录。
- 测试文件统一为 `<source-name>.test.ts`。源码移动或重命名时，同步调整测试位置与 import。
- 纯类型、声明、barrel、常量、极薄适配层、已被上层测试覆盖的代码，不强制创建空测试文件。
- 任何新增可测试业务逻辑必须有相应测试覆盖。

## 编写规则
- 使用 AAA：Arrange / Act / Assert。一个测试聚焦一个行为，多行为应拆分。
- 测试必须独立：不得依赖执行顺序、其他测试数据、共享可变状态、残留文件、全局变量或 Mock 状态。
- 断言必须验证可观察结果与业务语义。避免 `toBeDefined`、`toBeTruthy` 等空断言。避免测试私有变量、内部临时函数、无关调用顺序、硬编码的界面文案和 prompt。
- 必测正常路径、失败路径、边界条件、分支。错误测试需验证实际错误语义，而非仅“抛出异常”。
- Mock 只用于隔离测试边界。禁止 Mock 被测对象、所有内部函数。

## 新增、修改与重构
- 新增业务逻辑时，必须同时新增或修改测试。无法合理 Unit Test 时，判断是否应使用 Integration / E2E 或调整模块边界。
- 修改测试前确认：保护的行为是什么、失败来自代码/测试/环境、是否存在真实行为变化、是否降低验证强度、是否应新增测试。
- 禁止仅为让测试通过而删除有效断言或放宽条件。
- 测试失败时不要立即修改测试。先定位是实现、测试还是环境问题；无法确定原因时，不得改断言消除失败。

## 覆盖率
新增业务代码行覆盖率目标：≥ 80%。覆盖率用于发现未覆盖代码，不是唯一质量指标。
